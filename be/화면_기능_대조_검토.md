# 검토1·검토2 화면과 현재 백엔드 대조

> **후속 결정·구현 (2026-11-01):** 아래는 사진 최초 대조 기록이다. 사용자는 현재 감각 6개 유지(조명 추가 없음), 메시지 20자, 독립 이모티콘, 업무 정보의 범위를 확정했고 AI 생성은 보류했다. 이후 실제 front 코드에 맞춘 004·005를 구현·로컬 검증했으므로 최신 준비 상태는 [FE 코드 연동 검토](./FE_코드_연동_검토.md)를 따른다. 아래 미지원 판정을 현재 확장 코드의 판정으로 읽지 않는다.

검토 대상: [검토1](./검토1.jpg), [검토2](./검토2.jpg), 001~003 SQL, DB/API 명세서, Supabase 진행 기록.

## 1. 판정과 검증 범위

사진의 기능 전체를 현재 백엔드가 지원하는 상태는 아니다. 기존 P1의 회사 가입·좌석·근무 상태·메시지·감각 기능은 SQL/API가 준비돼 있지만, 캐릭터 저장과 AI 생성, 조명 값 등 사진에 나타난 기능은 빠져 있다.

이전의 P1 누락 없음 판정은 당시 요구사항 대조 범위의 결과다. 이번 사진에는 그 범위보다 상세하거나 다른 기능이 있어 별도 대조가 필요하다. 특히 현재 감각 6개라는 기존 계약과 사진의 조명 포함 5개 슬라이더는 일치하지 않는다.

이번 검토는 이미지 육안 확인과 저장소 SQL/API 정적 대조다. 원격 DB를 직접 조회하거나 별도 팀원의 FE 코드를 실행하지 않았다. 사용자에게 확인받은 원격 상태는 Inthon 1층·76석·비공개 지도 버킷·파일 경로 연결 및 가입 코드 재발급이다. 실제 사용자 JWT의 회원가입·RPC·지도 다운로드 통합 검증은 여전히 남아 있다.

판정 용어:

- **기반 준비:** 저장/조회/변경 계약이 존재한다. 실제 FE 연동 완료를 의미하지 않는다.
- **FE 구현:** 기존 데이터를 가공·표시하여 구현 가능하다. 별도 저장 데이터가 반드시 필요한 것은 아니다.
- **추가 BE 필요:** 현재 저장 구조·권한·API에 필요한 기능이 없다.
- **정책 확인:** 화면만으로 동작 의미가 확정되지 않는다.

## 2. 검토1 — 캐릭터 설정

| 화면 항목 | 현재 상태 | 필요한 작업 |
|---|---|---|
| 프로필 설정 시작·다음·이전 이동 | FE 구현 | 화면 이동 자체는 FE. 중단 후 이어하기까지 원하면 진행 상태 저장 계약 추가 |
| 사진 업로드로 AI 캐릭터 생성 | 추가 BE 필요 | 사진 저장 경로·업로드 권한·생성 요청·작업 상태·실패/재시도·결과 이미지 저장/조회가 모두 없음 |
| 직접 커스터마이징 선택 | 추가 BE 필요 | 선택 방식을 저장할 필드와 본인 캐릭터 저장 API가 없음 |
| 머리 모양·머리 색·눈 색 선택 | 추가 BE 필요 | 스타일 ID/색상 ID 저장 및 검증, 조회 API 추가. 선택 UI·미리보기는 FE |
| 기본 의상·성별 스타일·색상 조합 | 추가 BE 필요 | 의상/스타일 ID와 색상 조합 저장 구조 추가. 화면의 성별 탭은 외형 선택 분류이며 계정의 실제 성별 저장 요구로 단정하지 않음 |
| 빨강·노랑·연두·보라 특별 스킨 | 추가 BE 필요 | 스킨 ID와 활성 외형 저장, 허용 스킨 검증·변경 API가 없음 |
| 초기화·무작위·미리보기 | FE 구현 + 저장 연계 | 임시 선택은 FE에서 처리 가능. 완료를 누른 뒤 다른 기기/로그인에서도 유지하려면 저장 API 필요 |
| 완료하기·이후 스킨 변경 | 추가 BE 필요 | 저장 완료 판정, 본인 변경 권한, 최종 외형 조회 계약 추가 |

근거: `employees`는 id/user_id/company_id/seat_id/name/job_title/role/시각 컬럼만 저장한다. `sensory_profiles`는 민감도·설명용이어서 외형 설정과 다르다. public RPC에는 캐릭터 생성·저장·조회가 없고 Storage는 office-maps만 설정한다.

캐릭터 이미지·레이어를 FE 정적 파일로 준비하더라도 각 직원의 선택값을 동료 화면과 재로그인 후 복원할 수 있는 저장 구조는 필요하다. 사진 업로드는 AI 변환을 자동으로 수행하지 않는다. SQL만으로 이미지 생성 서비스가 생기는 것도 아니다.

## 3. 검토2 — 사무실 대시보드

| 화면 항목 | 판정 | 현재 근거와 한계 |
|---|---|---|
| 이름·직책 | 기반 준비 | employees.name/job_title, 본인 허용 컬럼 UPDATE |
| 내 직원 구분 | FE 구현 | get_my_membership.employee_id와 카드 employee_id 비교 가능 |
| 회사·층·좌석 위치 | 기반 준비 | floors/seats, 카드 seat의 층·좌석명·비율 좌표 |
| 층 선택 | 기반 준비 + 데이터 범위 | 여러 floors를 저장·조회할 수 있으나 현재 등록 데이터는 1층뿐. 화면 예시 3층은 실제 추가 등록 필요 |
| 디자인팀 등 팀 표시·필터 | 추가 BE 필요 | employees에 팀/부서 필드와 팀 테이블·응답이 없음. job_title은 직책이며 팀 이름의 대체 필드가 아님 |
| 전체·출근·자리 비움·퇴근 인원 | FE 구현 | 카드의 status로 집계 가능. 모든 페이지와 동일 필터 범위를 사용해야 함. 화면 기본안은 working/away/off_work 상호 배타 집계 |
| 동료 목록·이름/직책 검색·상태 필터 | FE 구현 | get_sensory_cards로 전체 카드 조회 후 처리 가능. 서버 검색/집계 API는 없으며 인원이 많아지면 별도 최적화 검토 |
| 동료 아바타·지도 위 개인 캐릭터·내 프로필 캐릭터 | 추가 BE 필요 | 사람별 외형 저장 및 카드 응답이 없음. 공통 기본 캐릭터 한 종류 표시만은 FE로 가능 |
| 지도 위 직원의 좌석 위치 | 기반 준비 | 선택된 seat_id와 비율 좌표로 위치 표시. 캐릭터 그림·애니메이션·말풍선 렌더링은 FE |
| 출근·자리 비움·퇴근 | 기반 준비 | set_employee_status. lunch/meeting/outside 사유 지원 |
| 말풍선·상태 메시지 작성/수정 | 기반 준비 | set_status_message. working/away만 작성, 퇴근 시 삭제 |
| 빠른 상태 버튼 | 조건부 FE 구현 | 버튼 클릭을 '☕ 커피 마실 사람~' 같은 텍스트 저장으로 연결 가능. 별도의 고정 아이콘 ID·종류·색을 일관되게 저장하려면 추가 계약 필요 |
| 점심·회의 버튼과 근태 연계 | 정책 확인 | 메시지만 바꿀지 away와 사유까지 바꿀지 결정 필요. 현 API는 메시지와 근태를 별도로 변경하므로 두 작업의 동시 성공이 필요하면 결합 RPC 추가 |
| 메시지 입력의 13/50 표시 | 계약 불일치 | 사진은 50자 제한으로 보이고 현재 DB/RPC는 200자. FE를 50자로 제한하면 화면 구현은 가능하나 서버까지 50자를 보장하려면 제약·함수·문서를 변경 |
| 현재 소음·온도·습도·냄새 | 기반 준비 | noise/temperature/humidity/odor_level, 1~5 또는 NULL, 본인 RPC 변경 |
| 현재 조명 슬라이더 | 추가 BE 필요 | 현재 조명/조도 컬럼이 없음. patch에 새 조명 키를 보내면 INVALID_SENSATIONS로 거부됨 |
| 업무 정보 탭 | 정책 확인 | 이름·직책 외에 무엇을 표시하는지 사진에 내용이 없어 완료 판정 불가. 일정·프로젝트·업무 상태를 임의로 추정하지 않음 |
| 작은 지도·층 선택·확대 버튼 | FE 구현 | 지도 원본·층·좌석 좌표는 제공. 확대/축소·뷰 전환은 FE |
| 소음 등 감각 지도 색상 | 일부 기반 준비 | 좌석별 4개 감각 원본·좌표는 제공. 연속 그라데이션/보간 규칙은 없음. 필요 시 FE에서 계산 가능하므로 반드시 BE 추가라고 판단하지 않음 |
| 화면 하단 '조용함 ↔ 시끄러움' 범례 | FE 구현 | noise_level 1~5와 연결 가능. 미입력/빈자리/퇴근은 별도 처리 |
| 상단 돋보기 | 정책 확인 | 동료 이름·직책 검색이라면 기존 데이터 활용 가능. 통합 검색이면 검색 대상·권한을 추가 정의 |
| 알림 종 아이콘 | 정책 확인 / 실제 알림은 추가 BE 필요 | 알림 발생 조건·수신자·읽음 여부·조회/변경 API가 없음. 아이콘 표시만 FE로 가능 |
| 프로필 드롭다운 | 정책 확인 | 로그아웃은 Auth 지원, 이름·직책 수정은 지원. 외형 변경·알림 설정 등 메뉴에 따라 추가 구현 필요 |

동료 목록에 사용자가 12명 표시되거나 전체 74명이 표시되는 것은 화면 예시이며, 76개 좌석이 등록되어 있다는 사실과 다르다. 좌석 수와 직원 수를 같은 숫자로 사용하면 안 된다.

화면에는 5초 이내 갱신인지 즉시 갱신인지가 표시되어 있지 않다. 현재 계약은 활성 탭 5초 polling이며 비공개 Broadcast와 즉시 동기화는 미구현이다. 화면 이미지 자체로 실시간 기능이 요구되었다고 단정하지 않는다.

## 4. 먼저 해결할 사항

### A. 화면 구현을 직접 막는 데이터/API 누락

1. **캐릭터 영속 저장:** 직원별 외형 구성·선택 스킨을 저장하고 본인만 변경, 같은 회사 직원이 표시용 외형을 조회할 수 있도록 설계한다. get_sensory_cards 및 필요한 내 정보 응답에도 외형을 연결한다. 허용 가능한 스타일/스킨 ID는 FE 에셋 목록과 합의한다.
2. **사진 기반 AI 생성:** 수동 외형 저장과 별도 작업이다. 원본 업로드·생성 실행 경로·진행 상태·결과 저장·실패 처리와 접근 권한을 설계해야 한다. 생성용 서버 비밀키를 FE 코드에 넣는 방식은 사용하지 않는다.
3. **조명:** 현재 체감 1~5로 받을지 실제 lux 측정값인지 먼저 정한다. 기존 체감 모델에 맞춘 1~5 주관적 밝기라면 새 컬럼뿐 아니라 patch 허용 키·검증·UPDATE·퇴근 초기화·응답·테스트·FE 문서를 함께 확장한다. visual_sensitivity는 평소 시각 민감도이므로 현재 조명과 대체할 수 없다.

### B. 화면과 맞춰 결정할 사항

1. 현재 감각은 기존 6개를 유지하고 조명을 더해 7개로 할지, 사진의 5개로 변경할지 결정한다. 기존 불쾌지수·혼잡도는 명시적 합의 없이 제거하지 않는다.
2. 팀 단위 표시/필터가 실제 기능이면 회사별 팀과 직원 연결을 추가한다. 단순 화면 예시라면 문구를 실제 데이터 범위에 맞춘다.
3. 메시지 최대 50/200자, 빠른 상태 버튼의 메시지·근태 처리, 아이콘을 텍스트에 포함할지 별도 필드로 저장할지 정한다.
4. 업무 정보·알림·상단 검색·프로필 메뉴의 실제 동작과 포함 범위를 정한다.
5. 감각 지도는 좌석별 색상인지 연속 보간인지, 미입력·퇴근·자리 비움의 표시와 보간 포함 여부를 FE와 합의한다.

### C. 변경 적용과 실제 검증

이미 001·002가 적용된 프로젝트이므로 수정된 001을 다시 실행하지 않는다. 기존 데이터를 보존하는 별도 후속 마이그레이션을 작성한다. 관련 권한·RLS·RPC·카드 응답·명세서를 함께 수정한다.

추가 후 검증: 외형 저장 후 재로그인/다른 기기에서 복원, 동료 외형 조회·타사 차단·타인 수정 차단, 조명 범위/부분 수정/퇴근 초기화/동시성, AI 성공·실패·원본과 결과 접근, 기존 가입·좌석·퇴근 기능 회귀 확인. 실제 사용자 JWT와 FE 연동 검증을 수행한다.

## 5. 이번 검토에서 한 일

- 사진의 보이는 기능과 DB·함수·권한·API의 대조 결과를 기록했다.
- 기존 명세서의 누락 없음 판정을 이번 사진 전체에 확대하지 않았다.
- 실제 DB 스키마·데이터·SQL 함수는 변경하지 않았다. 이 보고서의 추가 설계안은 아직 구현된 기능이 아니다.
- 사진의 표시만으로 확인할 수 없는 알림·업무 정보 등은 미정으로 남겼다.
- 커밋·푸시는 이번 요청에 포함되지 않아 수행하지 않았다.
