# P1 설계 검토 결과

> **2026-11-01 확장:** 이후 확정된 20자 메시지·독립 이모티콘·업무 정보와 실제 FE 캐릭터에 대한 004·005 구현·검증은 [FE 코드 연동 검토](./FE_코드_연동_검토.md)를 따른다. AI 생성은 보류, 현재 감각은 기존 6개 유지다. 이 문서 아래의 초기 P1 검증과 구분한다.

> **사진 기준 추가 검토:** 아래 판정은 기존 P1 범위의 기록이다. 이후 제공된 검토1·검토2에는 캐릭터/AI 생성·조명 등 현재 미지원 항목이 있다. 사진 전체에 대한 준비 상태는 [화면 기능 대조 검토](./화면_기능_대조_검토.md)를 따른다.

> 후속 적용 현황: 사용자가 001·002를 실제 프로젝트에서 실행했고 Inthon 1층·76석과 지도 경로 연결을 확인했다. 상세 근거와 미검증 범위는 [Supabase 진행 기록](./Supabase_진행_기록.md)을 따른다. 아래 로컬 검증 기록과 구별한다.

검토일: 2026-10-31. 기준: 기존 검토 문서의 D01~D12/P1 대조표 및 이후 사용자 결정.

## 1. 판정

검토 시작 시 DB 명세서는 직원·퇴근 정책 위주였고 API 명세서는 상태·메시지 위주여서 전체 설계가 완료된 상태가 아니었다. 이번 작업에서 빠진 테이블 상세, API, 권한, 운영 절차를 보완하고 전체 초기화 SQL을 작성했다.

아래 대조 범위의 P1 DB·API 설계 항목은 모두 문서와 SQL/SDK 계약에 연결했다. 모든 제품 정책이 사용자에게 확정되었다거나 실제 Supabase 배포가 완료되었다는 의미는 아니다. 남은 기본안·통합 검증은 4절에 구분했다.

## 3. 실행 검증

Docker의 PostgreSQL 17에서 실제 초기화 SQL을 실행했다. 로컬 테스트는 auth.uid(), auth.users, Storage 메타데이터/정책 표면을 최소 모형으로 제공하며 Supabase 서비스 자체를 실행한 것은 아니다.

검증 파일: tests/bootstrap.sql, tests/scenarios.sql, tests/run_sql_checks.py. 재현은 빈 임시 postgres:17-alpine 컨테이너 `sensespace-sql-review-20261031`을 준비하고 `python be/tests/run_sql_checks.py`를 실행한다. 실행마다 새 테스트 DB를 만든다. 테스트 파일은 실제 Supabase에 실행하지 않는다.

통과한 내용:

- SQL 전체 설치 및 프로필·상태·감각 자동 생성.
- 비로그인 차단, 회사별 회사/직원/프로필/상태/감각/지도 행 격리, 카드 목록·페이지·소속 조회.
- 직원 user_id 조회·코드 조회·권한/좌석 직접 변경·상태/감각 직접 변경·직원 삭제 차단. 동료 이름 변경은 0행.
- 퇴근 중 메시지·감각 차단, 잘못된 상태 전이·사유·감각 값·문자열·소수·알 수 없는 키·빈 patch 거부.
- 출근·자리 비움·퇴근, 부분 감각 변경·null 삭제, 퇴근 시 메시지·감각 초기화와 좌석·프로필 유지, 반복 퇴근.
- 타회사 좌석 선택 차단, 점유 좌석 충돌 후 기존 배정 유지, 복합 FK 회사 관계 검사.
- 코드 정규화, 같은 회사 재가입, 다른 회사 재가입 차단, 실패 호출 누적과 가입 호출 제한.
- 실제 두 세션의 메시지→퇴근 / 퇴근→메시지와 감각→퇴근 / 퇴근→감각 동시 실행. 상태 행 잠금 대기 후 최종 퇴근·빈 메시지·감각 NULL 확인.
- 실제 두 세션의 같은 좌석 선택, 같은 계정의 서로 다른 회사 동시 가입.
- 만료·폐기 코드 거부, 호출 제한 시간 구간 초기화, 메시지 200자 초과·NULL 거부, 잠금 전용 private 함수 실행 차단.
- 직원 210명에 대한 모든 카드 커서 페이지 조회. 누락·중복 없이 전체 조회 확인.
- `002_company_setup_example.sql` 실행 후 회사·층·좌석 2개·24자리 가입 코드 생성 확인. 지도 파일 업로드 자체는 미검증.

후속 지도 설정: 실제 `fe/정보관_1층.png`(4938×2868px)를 확인했고 사용자는 모든 의자를 등록하기로 결정했다. 002의 예시 좌석 2개를 전체 의자 76개의 좌표로 교체했다. 사용자가 [확인용 지도](./seat_map_preview.html)에서 번호·배치를 확인 완료했고 회사명을 `Inthon`으로 확정했다. 위 PostgreSQL 실행 검증은 교체 전 좌석 2개 버전의 결과이며, 변경한 76개 VALUES 데이터는 개수·이름 중복·좌표 범위를 정적으로 확인했다. 실제 Supabase에서 002는 아직 실행하지 않았다.

SQL 설치 성공과 업무 테스트 통과를 실제 Supabase Auth/Storage HTTP 통합 테스트 통과로 대체하지 않는다.

## 4. 기본안과 남은 확인

사용자 확정: FE 직접 Supabase, 한 회사 소속, 퇴근 좌석 유지, 메시지 삭제, 퇴근 중 메시지 변경 금지.

기존 기본안과 구현 선택: 좌석 없는 출근 허용, off_work→away 금지, 명시적 좌석 해제, 메시지 200자·설명 1,000자 등 길이 제한, 민감도 초기 NULL, 계정당 가입 5회/분, 활성 탭 5초 갱신. 표시 색상·민감도 문구·토글 복수 선택은 FE 협의 사항이다. 이 기본안들은 새로운 사용자 확정으로 기록하지 않았다.

원격 프로젝트에서 남은 작업: Supabase 설정/기존 객체 충돌 확인, 실제 이메일 인증·사용자 JWT·Data API·Storage signed URL 연동, 실제 좌표 QA·대규모 페이지·재연결 UI 검증. 실행용 SQL과 적용 안내를 제공했으며 원격 실행은 하지 않았다.

현재값 중심 P1 범위 밖: 이력·출퇴근 집계·센서·추천·지도 편집·직원 탈퇴·회사 이동·관리자 UI·즉시 반영 Broadcast. IP/복수 계정 공격 제한은 계정별 가입 제한만으로 해결하지 않는다.

## 5. SQL 파일 구분

001은 기존 초안에 의존하지 않는 새 프로젝트용 전체 설치 SQL이다. 이미 테이블이 있으면 중단하며 DROP/데이터 삭제를 수행하지 않는다. 002는 운영 초기 데이터 예시이므로 실제 정보로 수정 후 실행한다. 기존 문서 안의 부분 수정 SQL과 혼합하지 않는다.
