# Senspace v2 FE와 현재 BE 대조 검토

> 후속 진행: 이 검토 이후 사용자 요청에 따라 [006 자리 이동·복귀·자유 사유](./자리이동_복귀_API.md)를 구현하고 로컬 검증했다. 이후 사용자가 Supabase 적용·설치 확인 성공을 확인했다. 실제 직원 세션과 FE 통합 검증은 남아 있다. 기본/자유 사유는 상호 배제하며 팀 영역 BE 저장은 하지 않기로 확정했다. 나머지는 FE 확정 후 결정한다. 아래 내용은 006 구현 전 검토 기록이다.

검토일: 2026-11-01. 이번 변경은 검토 문서 추가뿐이다. SQL, Supabase, FE 원본은 변경하지 않았다.

## 1. 결론과 검토 범위

**추가 BE 작업이 필요하다. 기존 P1 기반은 재사용할 수 있지만, 새 FE의 캐릭터·좌석 계약과 P2 위치·집계 계약은 아직 맞지 않는다.** 또한 FE의 일부 동작이 앞서 확정한 요구와 달라서 BE만 추가해도 완성되지는 않는다.

검토 대상은 사용자가 지정한 다음 파일과 같은 폴더의 `sprites.js`, `support.js`, 저장소의 001~005 SQL·API 명세·P2 요구·집계 최종안이다.

- 원본: `C:\Users\New\Documents\카카오톡 받은 파일\Metaverse office sensory awareness\Senspace v2.dc.html`
- HTML SHA-256: `9D768DE304B856F0E3F8E8D663FEB78B3398CDF5E862056EBA1CEE2A708D215B`
- HTML 897줄, 110,215바이트. 아래 HTML 줄 번호는 이 버전 기준이다.
- 코드 정적 검토다. 브라우저 렌더링, 원격 DB 직접 조회, 실제 계정 통합 테스트는 수행하지 않았다. Supabase 적용 여부는 [기존 사용자 확인 기록](./Supabase_진행_기록.md)을 따른다.

## 2. 기존 BE를 연결하면 되는 부분

| 기능 | 현재 기반 | 연결 시 주의 |

새 HTML은 `people: P0`의 가상 직원 18명으로 시작하고(583~602, 631줄), `updMe()`가 React 상태만 바꾼다(652줄). 팀 영역과 알림 설정만 localStorage에 저장한다(637, 867, 890줄). Supabase 클라이언트·직원 데이터 호출·동료 데이터 구독은 없다. `support.js`의 fetch는 문서/스크립트 로딩이며 업무 데이터 연결을 의미하지 않는다.

따라서 실제 계정으로 저장·재로그인 복원·다른 직원에게 공유되는 동작은 **FE 연동 작업**이 필요하다. 이 이유만으로 별도 백엔드 서버를 새로 만들 필요는 없으며 기존 Supabase 직접 호출 구조를 유지할 수 있다.

## 3. 구현 또는 확장이 필요한 BE

### 3.1 새 캐릭터 형식 지원 — 연동 전 우선 해결

현재 `save_character`는 이전 `fe/src/character.js`의 7개 필드 형식을 검증한다. 머리·눈·의상은 정수 인덱스이며, `skin`은 특별 스킨 ID다. 005의 52개 카탈로그도 이 이전 FE 기준이다.

새 FE의 `cfg`는 아래처럼 다른 의미와 구조를 갖는다(`sprites.js`의 `SP.defaultChar`).

```json
{"hair":"bob","hairColor":"#5a3a2a","eye":"#3b2a2a","skin":"#ffd4b0","outfit":"shirt","top":"#4a86d8","bottom":"pants","pants":"#4a4e72","special":null}
```

- 머리 ID가 달라지고 눈·색상이 HEX 문자열이다.
- 피부색, 상의색, 하의 종류·색을 따로 선택한다. 기존 7개 카테고리만으로 이 선택들을 모두 보존할 수 없다.
- 특별 스킨은 기존 4개에서 동물 포함 8개다. ID도 red 계열에서 a_red 계열 등으로 다르다.
- 이름이 같은 필드라도 `skin`처럼 의미가 달라 자동으로 같은 값으로 취급하면 안 된다.

**필요 작업:** 새 렌더러 기준의 버전 구분·카탈로그·저장 검증·조회 형식과 기존 저장값 변환 정책. 현재 `cfg`를 그대로 기존 RPC에 넘기면 검증에서 거부된다. 기존 005를 다시 실행하거나 이전 카탈로그 생성기로 새 값을 덮어쓰는 방식은 사용하지 않는다.

### 3.2 공간 계층과 임시 이동·복귀 — 아직 미구현

현재는 회사 → 층 → 배정 좌석까지만 있다. P2의 공간 이름·유형·영역·정원·고정 특성과 좌석의 공간 소속이 없다. 우선 정보관 1층 전체를 하나의 업무 공간으로 시작한다는 결정은 유지한다.

추가로 필요한 저장·API 동작은 다음과 같다.

- 원래 배정 좌석과 임시 목적지 좌석을 분리한다.
- 이동 시 자동 away, 복귀 시 working, 이동 중 퇴근 시 목적지 해제. 퇴근 중 이동은 차단한다.
- 이동·재이동·복귀·실제 출근 전환에서 감각 6개를 모두 NULL로 초기화하고 관측 범위를 새로 구분한다.
- 다른 직원의 배정 좌석 및 임시 점유 좌석을 대상으로 할 수 없도록 동시 요청을 원자적으로 판정한다.
- 조회는 원래 자리·현재 위치·공간 계층·근태를 제공한다. 원래 자리 잔상을 별도 사람/재실 인원으로 세지 않는다.
- 자유 자리비움 사유 최대 20자를 기존 상태 메시지와 별도로 저장·검증하고 복귀/퇴근 때 지운다.
- 공간 현재 인원·정원·집계 점수·응답 수·최근 입력 시각을 조회한다. 숫자 opacity는 FE에서 정한다.

새 FE의 `confirmSeat()`는 직원의 단일 seat를 바꾸고 work로 전환한다(874줄). 원래 자리 보존·임시 목적지·복귀 동작은 없다. 이를 그대로 choose_seat에 연결하면 P2 이동 요구를 만족하지 못한다. 기존 choose_seat는 **배정 좌석 변경용**으로 유지한다.

현재 근태 RPC는 퇴근할 때 감각을 NULL로 만든다. P2의 출근·이동·복귀와 관측 범위를 함께 관리하는 강화된 전이는 아직 없다.

### 3.3 확정한 감각 집계와 Supabase 데이터 연결 — 아직 미완료

[집계 계산 모듈](./aggregation/sensory-aggregation.mjs)과 [최종 계산 계약](./감각_집계_최종안.md)은 있다. 하지만 Supabase의 공간별 관측 데이터를 읽어서 FE에 점수를 반환하는 연결은 아직 없다.

필요한 것은 공간·항목별 최신 입력과 실제 입력 시각, 현재 근무/방문 관측 범위다. 기존 current_sensations.updated_at은 6개 항목이 공유하므로 각 항목의 입력 시각으로 사용할 수 없다.

- 직원별·공간별·감각별 최신 유효 입력 하나만 반영한다.
- 반감기와 고정 30분 구간 보정을 적용하고 미입력/퇴근자/지난 근무·방문 관측을 제외한다.
- 같은 값 재전송이나 다른 항목 수정으로 기존 항목의 입력 시각을 갱신하지 않는다.
- 이동/출근 후 NULL을 3점으로 대체하지 않고, 유효 응답이 없으면 점수도 NULL이다.
- 새로운 입력 및 유효 대상 변경 시 일관된 데이터로 재계산한다. 새 입력·유효 대상 변경 없이 시간만 흘렀다고 점수가 바뀌지 않아야 한다.
- FE가 슬라이더 한 번을 조작할 때 발생하는 연속 이벤트는 불필요한 전체 항목 재저장으로 연결하지 않는다.

새 FE의 `miniHeat`는 출근 직원 개인의 좌석값에 방사형 색상을 그린다(774~775줄). 공간별 최종 가중 점수 계산이 아니며, 임시 이동한 away 직원도 현재 코드에서는 빠진다. BE가 공간 점수를 제공하고 FE는 이를 표시하도록 연결해야 한다. 불쾌 지수는 확정한 개인 입력 가중 평균을 유지한다.

### 3.4 업무 정보·근태 시각의 저장 계약 — 일부 결정 필요

새 FE는 직무(job), 직책(rank), 현재 업무(task)를 별도로 표현한다(578, 633, 753, 785~786줄). 현재 DB에는 업무 명칭용 job_title 하나와 보안 권한용 role이 있다. 세 값을 각각 유지하려면 저장 필드·검증·조회 계약을 확장해야 한다. rank를 관리자 권한으로 해석하지 않는다.

`since`도 '09:10', '18:30' 같은 문자열 데모다(582, 748줄). 근태가 시작된 시각을 실제로 표시하려면 서버가 기록한 전환 시각이 필요하다. 기존 status.updated_at은 메시지/이모티콘 변경에도 갱신되므로 이를 무조건 출근/자리비움 시작 시각으로 사용하면 안 된다.

### 3.5 빠른 아이콘·기본 자리비움 사유 목록 조정

새 QUICK의 12개 ID는 coffee/lunch/mute/hot/smell/eye/focus/rest/help/heart/phone/meeting이다(574~577줄). 기존 DB의 12개 ID와 서로 다르다. 최종 목록이 새 목록이라면 카탈로그 추가·비활성화·표시 매핑을 설계해야 한다. 아이콘 변경이 감각 수치나 메시지를 자동 변경하는 뜻은 아니다.

기본 자리비움 사유도 FE에는 meal/meeting/outside/short/personal/home이 있지만 BE는 lunch/meeting/outside만 허용한다. meal↔lunch 매핑만으로 나머지 사유까지 해결되지 않는다. 기존 합의대로 자유 사유는 별도로 지원하되 **새 기본 사유를 자동으로 추가하지 않는다.** 특히 재택(home)을 물리 공간 인원·감각에 반영할지는 별도 결정이 필요하다.

### 3.6 팀 영역 공유·알림 — 원하는 범위에 따라 추가

**팀 영역 드래그:** 마우스 좌표 계산과 선택 사각형은 FE에 이미 있다(864~867줄). 현재 저장은 브라우저 localStorage의 단일 `senspace.team`이다. 화면에는 디자인팀이 고정 표시되며, 영역 선택으로 직원의 팀 소속이 바뀌지는 않는다.

- 개인이 해당 브라우저에서 보는 범위를 저장하는 목적이면 현 방식은 FE에서 처리할 수 있다.
- 다른 기기에서도 개인 설정을 복원하려면 사용자별 설정 저장이 필요하다.
- 회사 구성원이 같은 팀 구역을 공유하려면 회사·층·팀·지도 버전에 연결한 영역 저장/조회와 편집 권한이 필요하다.
- 조직 팀, 보기 영역, 감각 집계 공간을 자동으로 같은 것으로 취급하지 않는다. 팀 영역을 그렸다고 초기 단일 업무 공간을 나누거나 직원을 자동 배정하지 않는다.

**알림:** 기존 notifications는 본인 좌석 변경 알림과 본인 읽음 처리 기반이다. 새 설정 UI가 원하는 동료의 근태·복귀·메시지 알림을 자동 제공하지 않는다. 즐겨찾기 관계, 개인 설정 저장, 대상 이벤트·전달 범위가 별도 필요하다. 새 FE의 scope(team/floor/fav), quiet 설정은 실제 수신 판정에 연결되어 있지 않고 testNotif은 고정 예시 문구다(658~661, 889줄).

탭이 열려 있을 때의 이벤트 수신과 OS 알림 표시는 FE에서 기존 조회/이벤트 연동을 활용할 수 있다. 탭 종료 뒤에도 알리는 Push 전달이 필요한지는 아직 결정되지 않았으므로 자동으로 추가하지 않는다.

지도 줌 배율과 `showText` 판정은 이미 FE가 처리한다(681, 696줄). BE에 줌 컬럼·배율별 API를 만들 필요는 없다. 이번 검토에서는 확대·축소를 수정하거나 새로 구현하지 않았다.

## 5. 지도·좌석 데이터의 중요한 불일치

기존 운영 데이터는 **Inthon 정보관 1층, 4938×2868 원본, 76개 좌석**이다. 라벨은 A-01 등이고 각 좌석은 UUID와 비율 좌표를 갖는다([좌석 원본](./seat_coordinates.json)).

새 HTML은 **1400×800 가구 조합 지도**이며, 문구는 센스컴퍼니/3층으로 고정되어 있다. `SEATS` 생성식(547~555줄)은 A/B/C 각각 16개, 총 **48개 선택 가능 좌석**을 만든다. 창가 의자 16개와 회의실 의자 12개는 그리기만 하고 SEATS에 넣지 않는다(556~558줄). 따라서 의자 그림은 총 76개여도 선택·직원 배치에 쓸 수 있는 데이터는 48개다.

**새 FE 좌석 라벨을 기존 DB 좌석 라벨에 단순 대응시키거나 지도 크기만 바꿔서는 안 된다.** 예를 들어 기존 A 그룹은 창가인데 새 A 그룹은 책상 자리다. 라벨 A-1→A-01 보정만으로 실제 장소가 일치하지 않는다.

권장 초기 방향은 기존 승인된 1층 76석을 유지하고 새 FE가 실제 좌석 UUID·표시 좌표를 사용하도록 맞추는 것이다. 새 가구 조합 지도를 최종 지도로 채택하려면 76석 전부의 대응 관계와 새 지도 버전을 먼저 정한다. 검토만으로 기존 지도·좌석을 삭제하거나 재생성하지 않는다.

## 6. 초대·AI·알림 화면의 범위 해석

- 초대메일 화면의 이름·회사·수신 주소·7일 만료 문구는 고정 예시다(27~51줄). 현재 BE는 회사 가입 코드 방식이며 이 화면과 같은 개인 이메일 초대 발송·개인 링크 만료 계약은 없다. 실제 초대 기능으로 채택할지, 기존 가입 코드 흐름을 사용할지 결정 후 연결한다.
- 사진 생성은 FileReader로 사진을 읽은 뒤 `randomCfg()`를 호출하는 데모다(655~657, 805줄). 사진 분석이나 OpenAI 호출이 아니다. **AI 구현 보류 결정은 유지한다.**
- ‘내 주변 감각 변화’ 알림 항목이 새 UI에 있지만(627줄), 사용자가 최종안에서 제외한 환경 변화 알림을 이 화면만을 근거로 구현하지 않는다.
- 재확인·환경 변화 감지·신뢰도·의견 불일치·별도 변화 확인 절차를 추가하지 않는다. 모임/도움/감각 상태 분류도 UI 예시만으로 새로운 BE 이벤트로 확정하지 않는다.

## 7. 다음 작업 순서와 결정 사항

1. **데이터 계약부터 맞춘다:** 새 v2의 지도·76석 대응 및 캐릭터 형식을 정한다. 기존 운영 데이터와 저장된 캐릭터를 보존한다.
2. **기존 P1 연결:** 실제 Auth → 회사 가입 → 본인/동료 조회 → 배정 좌석 → 근태·메시지·독립 아이콘·감각 저장 → 재로그인 복원을 확인한다.
3. **P2 저장·전이 설계 확정:** 초기 단일 공간·목적지 점유·복귀·자유 사유·NULL 초기화·근무/관측 범위를 정리한다.
4. **집계 데이터 연결:** 항목별 입력 시각을 저장하고 최종 계산 모듈과 공간 조회를 연결한다.
5. **필요 범위의 공유 설정·알림:** 개인/공유 팀 영역과 알림 대상·전달 범위를 확정한 뒤 구현한다.

SQL 전에 남은 주요 결정은 새 지도/기존 지도 대응, 캐릭터 버전·변환 정책, 직무/직책/현재 업무의 저장 범위, 기본 자리비움과 자유 사유의 관계, 목적지 없는 자리비움·재택의 공간 집계 처리, 근무일 경계, 정원 제한 여부다. 팀 영역 공유와 알림은 해당 기능에 착수할 때 별도로 결정할 수 있다. 미정 사항을 새 HTML의 데모 값으로 자동 확정하지 않는다.

후속 통합 검증에서는 서로 다른 직원/회사 세션, 같은 목적지 동시 이동, 이동·출근 후 NULL 유지, 부분 감각 입력의 시각 보존, 퇴근 중 작성 차단, 저장한 캐릭터의 재로그인 복원을 확인해야 한다. 이번 정적 검토를 실제 서비스 전체 동작 검증 완료로 간주하지 않는다.
