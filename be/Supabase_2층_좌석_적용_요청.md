# Supabase 담당자에게 — Inthon 2층(발표실) 지도·좌석 추가 요청

안녕하세요. 프론트에 **2층 지도와 2층 업무석 93석**을 추가했습니다. 프론트는 이미 2층을 그리고 있고, 아래 DB 변경(층 1행 + 좌석 93행)만 들어오면 그대로 연결됩니다. 프론트 코드 수정은 필요 없습니다.

기존 마이그레이션(001~006)은 **다시 실행하지 말아 주세요.** 이번 요청은 순수 추가(additive)이며, 새 마이그레이션(예: `007_floor2_inthon.sql`)로 넣으시면 됩니다.

## 0. 회사 / 현재 상태

- 회사: Inthon, `company_id = ff484ad2-375d-416e-86fa-95e01f2b1323`
- 현재 이 회사에는 **1층만** 있습니다. (`floors`: `floor_number = 1`, `map_width 4938`, `map_height 2868`)
- 1층 좌석 76석(A-01 … I-xx)은 그대로 두고, **2층만 추가**합니다.
- 프론트에서 확인한 동작
  - 지도는 `floors`/`seats` 조회 결과로 그 층 좌석 마커를 만들고, 마커→`seat.id`로 `choose_seat`을 호출합니다.
  - 좌석 라벨을 키로 쓰는 프론트 내부 맵이 있어 **라벨은 회사 전체에서 고유해야** 합니다. 그래서 2층은 `J`, `K`, `L` 대(臺)를 씁니다. (1층은 A~I)
  - 2층 좌석이 DB에 없으면 프론트는 2층 지도는 그리되 선택 가능한 좌석 마커는 0개로 보여 줍니다. (그래서 아래 2-2가 필요합니다)

## 1. 프론트가 하는 일 (계약)

1. 2층 도면은 **프론트에 내장된 이미지**(`fe/src/assets/floor-2f.png`, 1713×918)로 그립니다. 서버의 `map_path`는 스키마 규칙상 값이 필요할 뿐, 지금 화면에는 쓰지 않습니다.
2. 좌석 선택/저장은 기존과 동일합니다. `seats`에서 받은 `id`로 `choose_seat` RPC를 호출합니다. 2층이라는 이유로 다른 API를 쓰지는 않습니다.
3. 프로필의 층 선택에는 회사 `floors`에 있는 층이 그대로 노출됩니다. 2층 행이 생기면 자동으로 `2층`이 선택지에 나타납니다.
4. 초대 링크의 입장 층은 `employee_links.floor_number` → `employees.preferred_floor_number`를 그대로 씁니다. 2층으로 입장시키려면 링크 발급 시 `p_floor_number = 2`로 넘기면 됩니다.

## 2. 필요한 변경

### 2-1. 2층(`floors`) 행 추가

```sql
-- 2층 층 행 추가 (이미 있으면 아무 것도 하지 않음)
WITH c AS (
  SELECT id FROM public.companies
  WHERE id = 'ff484ad2-375d-416e-86fa-95e01f2b1323'
), f AS (
  SELECT gen_random_uuid() AS floor_id
)
INSERT INTO public.floors(company_id, id, floor_number, map_path, map_width, map_height)
SELECT c.id, f.floor_id, 2,
       c.id::text || '/' || f.floor_id::text || '/v1/map.png',
       1713, 918
FROM c CROSS JOIN f
ON CONFLICT (company_id, floor_number) DO NOTHING;
```

- `map_width`/`map_height`는 **2층 도면 원본 크기(1713×918)** 입니다. 좌석 좌표가 이 기준으로 계산돼 있습니다.
- `map_path`는 `company_id/floor_id/…` 규칙만 만족하면 됩니다. 스토리지에 2층 이미지를 올릴 필요는 없습니다(프론트 내장 이미지). 올리실 거면 `v1/map.png`에 `fe/src/assets/floor-2f.png`를 그대로 올려 주세요. 경로가 달라지면 알려 주세요.
- 이미 2층을 만드셨다면 위 SQL은 건너뛰고, **좌석만** 넣어 주세요.

### 2-3. `choose_seat` 동작 확인

`choose_seat(p_employee_id, p_seat_id)`는 001 그대로면 됩니다. 다만 2층 좌석도 같은 회사/층 소속이므로 다음이 보장돼야 합니다.

- 다른 회사 좌석을 넘기면 거부 (`seats.company_id = employees.company_id` 확인)
- 이미 다른 직원이 쓰는 좌석이면 거부 (`employees.seat_id UNIQUE`)
- 정상 배정 시 `employees.seat_id` 갱신

2층 좌석 배정 후 `get_employee_location`/`get_sensory_cards`가 **2층 좌석 기준 좌표**를 돌려주는지 확인 부탁드립니다.

### 2-4. 조회 RPC에서 층/좌석 정보

- `get_sensory_cards`와 `get_my_membership`이 `floor_number`(=2)와 좌석 라벨(`J-12` 등)을 그대로 돌려주면 됩니다.
- `floors`의 SELECT 정책(`floor_read`)이 회사 소속 인증 사용자에게 2층 행도 보이게 해 주세요. 001의 정책이 회사 단위라면 추가 변경은 없습니다.

### 2-5. 초대 링크의 입장 층 (선택)

2층으로 바로 입장시키려면 링크 발급 시 `p_floor_number = 2`를 넘겨 주세요. 프론트는 이 값을 좌석 선택 화면의 초기 층으로 씁니다. 1층 링크는 지금처럼 `1`입니다.

## 3. 좌표 기준 (참고)

- 2층 도면 원본: 1713×918 (`fe/src/assets/floor-2f.png`)
- `x_ratio = 의자중심_x / 1713`, `y_ratio = 의자중심_y / 918`
- 행 구성
  - 상단(J): y ≈ 203 / 255 / 305 px, 10열
  - 중앙(K): y ≈ 432 / 487 / 542 px, 11열
  - 하단(L): y ≈ 676 / 729 / 782 px, 10열 (가운데 2열 비움)
- 프론트는 이 값을 그대로 써서 지도 위에 좌석 마커를 찍습니다. 좌표가 바뀌면 마커가 어긋나므로, 값을 수정하실 때는 알려 주세요.

## 4. 적용 후 확인 체크리스트

- [ ] `floors`에 Inthon 2층(`floor_number = 2`, `map_width 1713`, `map_height 918`) 1행
- [ ] `seats`에 2층 좌석 93행 (`J-01…J-30`, `K-01…K-33`, `L-01…L-30`)
- [ ] 2층 좌석 라벨이 1층(A~I)과 겹치지 않음
- [ ] `choose_seat`로 2층 좌석 배정 성공 / 중복·타사 좌석 거부
- [ ] `get_sensory_cards` / `get_my_membership` 응답에 2층 `floor_number`와 라벨 포함
- [ ] `floors` SELECT 정책으로 2층 행이 인증 사용자에게 보임
- [ ] (선택) 2층 링크 발급 시 `p_floor_number = 2`

확인용 쿼리:

```sql
SELECT f.floor_number, count(s.id) AS seats
FROM public.seats s
JOIN public.floors f ON f.id = s.floor_id
WHERE s.company_id = 'ff484ad2-375d-416e-86fa-95e01f2b1323'
GROUP BY f.floor_number
ORDER BY f.floor_number;
-- 기대값: 1 → 76, 2 → 93
```

1. 2-1로 **2층 층 행 1개** 추가
2. 2-2로 **2층 좌석 93석** 추가 (한 번만 실행해도 되고, 재실행해도 안전)
3. 2-3/2-4 동작 확인 후 결과 회신
4. (원하시면) 2층으로 입장하는 **테스트 링크 1~2개**도 `p_floor_number = 2`로 발급해 주세요. 받는 대로 2층 좌석 선택 → 저장까지 검증하고 결과 공유드리겠습니다.
